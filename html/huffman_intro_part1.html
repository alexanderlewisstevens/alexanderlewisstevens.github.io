Key Terms

The rest of the page defines and uses these terms without requiring the video.

Symbol

A unit of data being encoded. In examples this might be a letter. In the project it will be an RGB pixel color.

Code

The binary string assigned to a symbol. For example, A = 0 or blue = 11.

Leaf

A tree node with a symbol. Reaching a leaf tells the decoder that one complete symbol has been found.

1. Compression, Fixed-Length Codes, and Ambiguity

Computers store data as bits. If every symbol uses the same number of bits, decoding is simple because the decoder can split the bitstring into equal-sized chunks. Compression becomes possible when common symbols use shorter bitstrings and rare symbols use longer bitstrings.

A fixed-length code gives every symbol the same number of bits. With four symbols, two bits are enough because the possible two-bit strings are 00, 01, 10, and 11.

SymbolCode
A00
B01
C10
D11

Example. To encode BAD, replace each character with its code: B is 01, A is 00, and D is 11. The encoded bitstring is 010011.

Because each character costs 2 bits, this three-character message costs 3 x 2 = 6 bits.

Why variable-length codes can be ambiguous

Variable-length codes are not automatically safe. If one complete code is the beginning of another complete code, a decoder may not know where to stop.

SymbolCode
A0
B01
C10

The code for A, 0, is the beginning of the code for B, 01. That creates ambiguity.

Practice. If one encoded bitstring can decode into two different messages, which requirement has failed?

Practice. With A=0, B=01, and C=10, the bitstring 010 is ambiguous.

2. Frequent Symbols Should Usually Have Shorter Codes

Unequal frequencies make fixed-length codes wasteful. A shorter code helps most when it belongs to a symbol that appears often.

Example. Suppose A appears 60 times and B appears 5 times. Saving one bit on A saves 60 bits total, but saving one bit on B saves only 5 bits total. This is why frequent symbols usually belong closer to the root.

Practice. Using frequencies A=50, B=25, C=15, and D=10, which codebook is better?

Codebook 1: A=0, B=10, C=110, D=111

Codebook 2: A=00, B=01, C=10, D=11

3. Prefix-Free Codes Come from Tree Paths

The problem with variable-length codes is that the decoder needs a clean stopping rule. A prefix-free codebook solves this problem.

A codebook is prefix-free if no symbol's complete code is the beginning of another symbol's complete code. Prefix-free codes can be decoded from left to right without separators.

SymbolCodeLength
A01
B102
C1103
D1113

Example. Decode 0100 from left to right. The first 0 is A. The next bits 10 are B. The final 0 is A. So 0100 decodes to ABA.

4. Binary Trees as Codebooks

Binary trees give a visual way to define prefix-free codes. Starting at the root, each left edge appends 0 and each right edge appends 1. A symbol's code is the path from the root to its leaf.

Derived Code Table

SymbolPathCode
Aleft0
Bright, left10
Cright, right, left110
Dright, right, right111

Why the tree is prefix-free. Symbols only appear at leaves. If A is a leaf, the path to A stops there; no longer symbol can continue below A. That is why a leaf-based codebook avoids the ambiguity from Section 2.

    6. Frequency and Weighted Path Length

    Code length is the same thing as tree depth. A symbol at depth 1 costs 1 bit each time it appears. A symbol at depth 3 costs 3 bits each time it appears.

    Compression depends on how often each code is used. The cost contribution for one symbol is frequency x code length. The total weighted path length is the sum of those contributions.

    Symbol Frequency Code Code Length Frequency x Length
    A500150
    B2510250
    C15110345
    D10111330

    Total cost: 50 + 50 + 45 + 30 = 175 bits per 100 symbols.

    Average cost: 175 / 100 = 1.75 bits per symbol.

    7. Lossy Binning Before Huffman Coding

    Huffman coding is lossless for the symbols it receives. If the symbols are exact RGB pixels, then decoding should recover those exact RGB pixels.

    Image compression can also include a separate step before Huffman coding: nearby colors are placed in the same bin. This is lossy because the original colors are rounded. After that rounding, Huffman coding can still decode the binned image exactly.

    Example. Dropping 4 low-order bits from each color channel keeps the rough color and removes small differences. The value 213 has binary form 11010101. Keeping the top four bits gives 1101, then padding with zeros gives 11010000, which is 208.

    So (213, 66, 73) becomes (208, 64, 64).

    Lossless symbols

    Small color differences stay separate, so the tree needs more leaves.

    • (210, 64, 70)
    • (213, 66, 73)
    • (218, 71, 69)
    • (221, 78, 74)
    • (209, 70, 76)
    • (216, 69, 67)
    • (42, 120, 202)
    • (244, 202, 62)

    Lossy-binned symbols

    Nearby colors collapse into one symbol, so the tree can be smaller.

    • (208, 64, 64) for six red-like pixels
    • (32, 112, 192) for one blue pixel
    • (240, 192, 48) for one gold pixel
    Version What counts as a symbol Tree leaves Deepest leaf Average code length
    LosslessExact RGB pixels833.00 bits per pixel
    Lossy-binnedRounded RGB pixels321.25 bits per pixel

    The smaller tree does not mean Huffman forgot information. The information was simplified before Huffman coding began. The decoded lossy image should match the binned image exactly, not the original image exactly.

    Practice. Which version is more likely to have fewer leaves in its Huffman tree?

    8. How This Connects to the Project

    The full Huffman construction algorithm repeatedly combines the two lowest-frequency items. That idea is useful later, but it is not required for the first decoding project.

    Practice. Frequencies are A=40, B=20, C=15, and D=5. Which two symbols would be combined first?

    In the project, each decoded symbol is an RGB pixel such as (128, 64, 0). The starter files give you the tree and the compressed bitstring. Your job is to write the decoder that walks the tree and reconstructs the image.

    Important scope. You do not need to build the Huffman tree in this project. You do not need a heap or priority queue yet. You are practicing how to decode with a tree that has already been built.

    Decoder algorithm

    1. Start at the root of the provided tree.
    2. Read one bit from the encoded bitstring.
    3. Move left for 0 and right for 1.
    4. When you reach a leaf, append that leaf's pixel to the output.
    5. Return to the root and continue with the next bit.
    6. Raise an error for invalid bits or an unfinished path.

    Project vocabulary

    • Tree height: the length of the deepest root-to-leaf path.
    • Node depth: the number of edges from the root to that node.
    • Pixel count: should match width x height.
    • Checksum: a fingerprint used to verify that the decoded pixels are correct.
    • Compression ratio: encoded size divided by original size.

    File paths and hashmap counts

    The starter code expects all data files to be next to your Python script. Use pathlib.Path so the script works even when run from a different working directory.

    from pathlib import Path

here = Path(__file__).resolve().parent
bits_path = here / "encoded_image_bits.txt"
bits = bits_path.read_text(encoding="utf-8")
